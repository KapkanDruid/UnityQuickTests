# Testing Unity Quick Tests

[![Читать на русском](https://img.shields.io/badge/%D0%A7%D0%B8%D1%82%D0%B0%D1%82%D1%8C_%D0%BD%D0%B0_%D1%80%D1%83%D1%81%D1%81%D0%BA%D0%BE%D0%BC-blue)](TESTING.ru.md)

This document describes the package's reproducible test setup. Developers,
agents, and future CI use the same workflow.

## Quick Start

Run the following from the repository root:

```powershell
.\scripts~\run-tests.ps1 -Mode All
```

You can also run each test layer separately:

```powershell
.\scripts~\run-tests.ps1 -Mode EditMode
.\scripts~\run-tests.ps1 -Mode PlayMode
.\scripts~\run-tests.ps1 -Mode PlayerBuild
```

Results are saved in the local, gitignored `TestProject~/artifacts/` folder:

- `EditMode-results.xml` and `PlayMode-results.xml` contain machine-readable
  results.
- `EditMode.log` and `PlayMode.log` contain the full Unity logs.
- `PlayerBuildSmoke.log` contains the player build smoke-check log.

The script reports a failure if Unity exits with a nonzero code, does not create
an XML result file, or reports failed tests. For `PlayerBuild`, it also checks
that the build was created and that the output folder contains no
Editor/CodeGen/Cecil assemblies. Each layer has a five-minute timeout by default.
You can change this limit with `-TimeoutSeconds`.

## Test Host Project

A minimal Unity project lives in `TestProject~/`. It is tracked in Git and
references the current package checkout through a local dependency:

```json
"com.urbandruids.unity-quick-tests": "file:../.."
```

This lets you test uncommitted changes before publishing a new version.
The Unity version is pinned in `TestProject~/ProjectSettings/ProjectVersion.txt`.
Other `ProjectSettings` files generated by Unity on the first launch stay local
and are excluded from Git.

The `~` suffix is intentional. Unity ignores these folders when importing a UPM
package: the host project is downloaded with the Git repository, but it is not
imported into the user's project and does not require `.meta` files.

## Test Locations

```text
Tests/
  CodegenConsumer/ separate assembly for ILPP auto-registration smoke checks
  Editor/    fast Edit Mode checks of internal components
  Runtime/   Play Mode checks of behavior in the player loop
```

`Tests/Editor` covers:

- schedule attribute validation;
- hotkey attribute validation;
- `Once` and `Repeat` schedules;
- static hotkey invocation through a Scene View event;
- matching hotkeys against editor events;
- hotkey rising edges using deterministic fake input;
- resetting hotkey state between Play Mode sessions;
- reflection-based invocation and exception logging;
- discovery of supported and unsupported static methods;
- discovery of Unity object and plain C# instance methods;
- explicit policies for inherited methods, generic methods/types, async methods,
  and Task/UniTask-like return types;
- routing invocations to multiple `MonoBehaviour` instances;
- routing invocations to a loaded `ScriptableObject`;
- routing invocations to registered plain C# instances;
- ILPP constructor injection for plain C# service targets;
- preventing duplicate invocation when manual registry fallback is used after ILPP;
- `this(...)` constructor chaining without duplicate registration;
- fast `WillProcess` filtering for the CodeGen layer;
- rejecting player assemblies without the `UNITY_EDITOR` define in `WillProcess`;
- weak registry behavior: duplicate registration, unregistering, and GC cleanup;
- clearing the registry when entering and leaving Play Mode without domain reload;
- finding loaded `EditorWindow` instances through Unity resources;
- diagnostic warnings for duplicate hotkeys and hotkeys without modifiers;
- the registration report, including trigger, declaring type, target scope, and
  support status;
- an explicit status indicating that `ScriptableObject` lookup does not load
  assets through `AssetDatabase`;
- limiting warnings when an instance target is missing.

`Tests/Runtime` checks that `QuickTestInputPoller` actually receives `Update` in
the player loop and sends the event.

The `PlayerBuild` smoke check, run through `QuickTestPlayerBuildSmoke.Run`, builds
a minimal StandaloneWindows64 player and verifies:

- the absence of `UnityQuickTests.Editor`, `Unity.UrbanDruids.UnityQuickTests.CodeGen`,
  `Mono.Cecil`, and `Unity.CompilationPipeline.Common` assemblies in the output;
- the absence of the `QuickTestInputPoller` type in managed player script assemblies;
- the absence of calls to `QuickTestInstanceRegistry.Register` in managed player
  script assemblies;
- the presence of runtime quick-test attributes as harmless player metadata.

## Why Hotkeys Are Tested with Fake Input

Physical key presses and Unity window focus cannot be reproduced reliably in
headless mode. An internal interface therefore separates reads from `Input.GetKey`:

- production code uses the real `UnityEngine.Input`;
- unit tests control fake input and check the state machine without a keyboard;
- the real keyboard is covered by a short manual smoke check before release.

## Running Tests in the Unity Editor

For interactive diagnostics, open `TestProject~` as a regular Unity project and
run the tests through `Window > General > Test Runner`.

A consumer smoke test in the game project provides an additional check of real
package usage. The consumer project does not replace the minimal host: it has
its own dependencies and state, which must not affect the package's regression
tests.

## Checks That Still Require Manual Testing

- pressing an actual hotkey in Play Mode;
- pressing an actual hotkey in Scene View in Edit Mode.

## If Play Mode Was Forcibly Stopped

Forcibly stopping Unity during a Play Mode transition can leave a temporary
`InitTestScene` and an inconsistent host cache. If the next run hangs before
executing a test:

1. Make sure the `TestProject~` batchmode process has stopped.
2. Delete the local `TestProject~/Library`, `TestProject~/Temp`, and temporary
   `TestProject~/Assets/InitTestScene*.unity*` files.
3. Run `.\scripts~\run-tests.ps1 -Mode All` again.

These files are generated by Unity and are not tracked in Git.
